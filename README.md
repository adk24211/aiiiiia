# 손가락 마일리지 (KeyMiles)

내가 쓴 한글을 **두벌식 · 세벌식 390 · 세벌식 최종**으로 각각 쳤을 때
손가락이 실제로 몇 미터 움직이는지 재 주는 도구입니다.

서버가 없습니다. HTML·CSS·JS 파일만 있고, 계산도 파일 읽기도 전부 브라우저 안에서 끝납니다.

```
안녕하세요 오늘 날씨가 참 좋네요 …  (한글 69자)

  두벌식   4.46m   타건 218회   시프트 10회   SFB 1.82%   숫자행 0.0%
  390     5.29m   타건 213회   시프트  4회   SFB 1.25%   숫자행 9.8%
  최종     5.43m   타건 213회   시프트  5회   SFB 1.25%   숫자행 10.4%
```

세벌식이 타건 수·시프트·같은 손가락 연속에서는 이기는데 **이동거리는 오히려 22% 더 깁니다.**
자모를 숫자행까지 펼쳐 놓았기 때문입니다. 이 도구는 그 맞바꿈을 숫자로 보여 줍니다.

## 이동거리 모형

거리는 사실이 아니라 **모형**입니다. 그래서 세 가지를 모두 제공하고, 무엇을 쓰는지 화면에 적습니다.

| 모형 | 규칙 | 성질 |
|---|---|---|
| **표준** (기본) | 한 손가락이 키로 가는 동안 나머지 손가락은 홈으로 돌아온다 | 영문 자판 분석 도구(patorjk / stevep99 keyboard-layout-analyzer)와 같은 규칙 |
| 손가락 유지 | 친 자리에 그대로 머문다 | 순수한 좌우 이동. **같은 키 반복은 0** — `세`를 120번 쳐도 20번과 같은 값이 나온다 |
| 매번 홈 복귀 | 타건마다 홈에서 왕복 | 가장 엄격한 교본식 |

시프트는 세 모형 모두에서 **누르고 있는** 것으로 봅니다. `ㅆㅆㅆ`는 시프트 1회지 3회가 아닙니다.
그리고 시프트도 새끼손가락을 쓰는 타건이므로 같은 손가락 연속(SFB) 계산에 포함됩니다.

## 왜 믿을 수 있나

| 무엇 | 어떻게 |
|---|---|
| 자판 배열 3종 | libhangul 원본 `hangul/hangulkeyboard.h` 에서 **기계 추출**. 사람이 옮겨 적은 값 0개 |
| 자모 조합 규칙 36개 | 같은 파일의 `hangul_combination_table_default` |
| 한글 분해 | 유니코드 표준 3.12 (완성형 → 초·중·종성) |
| 회귀 방지 | `tools/verify-layouts.mjs` 가 CI에서 **매번 원본을 내려받아 대조** |
| 계산 검증 | `tools/test-engine.mjs` 골든 벡터 78건 (손으로 계산한 이동거리 포함) |
| 색 대비 | `tools/check-contrast.mjs` 가 팔레트와 히트맵 전 구간의 WCAG 대비를 계산해 검증 |

`한글 자판 실험` → 두벌식 `gksrmf wkvks tlfgja`, 이동거리 287.6㎜.
가장 단순한 경우인 `한`(= `gks`)은 손으로 검증했습니다: 왼손 검지가 `f`→`g` 1.0u 갔다가
다음 타건 때 되돌아오며 1.0u, 나머지 손가락은 홈에서 움직이지 않아 합계 2.000u × 19.05㎜ = 38.10㎜.

### 세벌식 ㅗ·ㅜ 두 자리 처리

세벌식에서 홑모음 ㅗ·ㅜ는 왼손 `v`·`b`, 겹모음(ㅘ ㅙ ㅚ ㅝ ㅞ ㅟ)의 **앞자리**로 쓸 때는
오른손 `/`·`9` 를 씁니다. 그래야 뒤따르는 모음과 손이 갈립니다.
libhangul 표에는 두 자리가 모두 들어 있고, 이 도구는 문맥에 따라 올바른 쪽을 고릅니다
(`과` → 세벌식 `k/f`). 이걸 구분하지 않으면 이동거리가 실제와 어긋납니다.

  style.css

`index.html` 을 그냥 열어도 동작합니다.

## 개발

```bash
node tools/verify-layouts.mjs   # 자판 데이터가 원본과 같은가
node tools/test-engine.mjs      # 계산이 골든 벡터를 재현하는가
node tools/test-kakao.mjs       # 파서가 4포맷을 읽는가
node tools/check-contrast.mjs   # 색 대비가 WCAG AA를 만족하는가
node tools/build-pages.mjs      # 서브페이지 다시 생성 (배열·지표를 바꿨다면 필수)
node tools/gen-og.mjs           # og.png 다시 생성
npx http-server -p 8099 .       # 로컬에서 띄우기
```

`assets/layouts.js` 는 생성물입니다. 자판 데이터가 틀렸다면 libhangul 원본을 확인한 뒤
이슈로 알려 주세요. 배열도를 눈으로 옮겨 적은 수정은 받지 않습니다 — 그게 이 프로젝트가
피하려는 오류의 원인입니다.

## 수익화 켜기

전부 `assets/config.js` 한 파일에서 켭니다. **값이 비어 있으면 해당 블록은 화면에 나오지 않습니다.**
그래서 아무것도 설정하지 않은 상태로 배포해도 광고 없는 완전한 도구로 동작합니다.

### 1일차에 바로 되는 것

| 항목 | 하는 일 |
|---|---|
| `coupangPartnerId` | 쿠팡 파트너스 가입 → 사이트 등록 → 트래킹 코드 입력. 넣는 즉시 결과 지표에 맞춘 추천 블록과 **법정 대가성 문구**가 함께 켜집니다 (문구는 페이지 최상단과 광고 블록 위 두 곳에 자동 노출) |
| `sponsorUrl` | GitHub Sponsors / BuyMeACoffee 링크 |
| `unlockUrl` + `unlockHashes` | `node tools/make-codes.mjs 200` 으로 코드를 만들고, 코드 목록은 판매처에, 해시 배열만 config에 넣습니다 |

### 도메인을 산 뒤에 되는 것

`adsenseClient` + `adsenseSlotTop` / `adsenseSlotBottom` — **`*.github.io` 로는 애드센스 승인이
나지 않습니다.** 부모 도메인(`github.io`)의 소유를 확인할 수 없고, `ads.txt` 도 루트에 올릴 수
없기 때문입니다. 커스텀 도메인을 붙이고(`CNAME` 파일 + DNS), `ads.txt` 의 주석을 풀어 본인
pub 번호를 넣은 뒤 신청하세요.

승인 심사가 보는 것들은 이미 갖춰져 있습니다:

- 개인정보처리방침 → `privacy.html` (모든 페이지 푸터에서 링크)
- 소개 / 문의 → `about.html` (`contactEmail` 을 채우면 이메일이, 비우면 GitHub 이슈가 표시됨)
- 충분한 콘텐츠 → 자판 소개 페이지 3종

`siteUrl` 도 같이 채우면 canonical·og:image가 절대 주소가 되고 `sitemap.xml` 이 생성됩니다.

### 개인정보처리방침은 설정에 따라 바뀝니다

`tools/build-pages.mjs` 가 `config.js` 를 읽어서 방침을 생성합니다.

- 광고를 **끈 상태**: 수집하는 것이 GitHub 접속 로그뿐이므로 방침도 그만큼만 (11개 조).
- `adsenseClient` 또는 `coupangPartnerId` 를 **켠 상태**: 쿠키, 제3자 제공, 국외 이전,
  맞춤형 광고 거부 방법 조항이 자동으로 들어갑니다 (개인정보 보호법 제30조 기재사항).

광고를 켰는데 `contactEmail` 이 비어 있으면 빌드가 경고합니다 — 보호책임자 연락처는
법정 기재사항입니다.

### 대가성 문구

`coupangPartnerId` 를 채우면 문구가 **페이지 첫 부분과 추천 블록 바로 위** 두 곳에 켜집니다.
공정거래위원회 「추천·보증 등에 관한 표시·광고 심사지침」은 본문과 명확히 구분되고 쉽게
인식되는 표시를 요구하므로, 본문보다 **큰 글씨 · 다른 색 · 테두리**로 넣었고 접히지 않습니다.
푸터에만 넣는 배치는 피했습니다. 제휴 링크에는 `rel="sponsored nofollow"` 가 붙습니다.

### 유료 언락에 대한 솔직한 말

서버가 없으면 라이선스 **검증**은 불가능합니다. 코드 해시 대조는 브라우저 안에서 일어나므로
마음먹으면 우회할 수 있습니다. 이 프로젝트는 그걸 숨기지 않고 화면에 그대로 적어 두고,
"쓸모 있었으면 정직하게 결제해 주세요"로 갑니다. 가짜 보안을 파는 것보다 낫다고 봅니다.

## 이 도구가 하지 못하는 것

- 손목·팔 이동은 재지 않습니다. 손가락 끝의 평면 이동만 잽니다.
- 손가락 길이 차이, 키 높이, 스태거 각도는 반영하지 않았습니다.
- 실제 타자에서는 다음 키를 미리 준비하며 손이 겹쳐 움직입니다. 이 모델은 순차 이동으로 단순화합니다.
- 영문·숫자·문장부호는 세 자판이 같으므로 계산에서 제외합니다 (제외한 글자 수는 화면에 표시).
- **의학적 조언이 아닙니다.** 피로는 자세·키압·휴식이 훨씬 크게 좌우합니다.
