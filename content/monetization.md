### 1.4 손가락 마일리지에 구체적으로 어떻게 넣나

이 사이트는 "게시물"이 아니라 **도구 페이지 하나**다. 지침의 "게시물의 제목 또는 첫 부분"을
정적 단일 페이지에 매핑하면 **"제휴 링크가 있는 섹션이 시작되기 전, 페이지에서 먼저 읽히는 위치"**가 된다. **[추론]**

권장 배치 (안전한 순서로):

1. **키보드 추천/제휴 링크 섹션의 `<h2>` 바로 아래, 링크보다 위**에 고지 박스.
   (링크와 같은 화면에 반드시 함께 보이게 — 스크롤해야 보이면 안 됨)
2. 제휴 링크가 **페이지 상단(첫 화면)에도 있다면**, 마스트헤드 바로 아래 **페이지 첫 부분에도** 한 번 더.
3. **푸터에만 넣는 것은 금지에 가깝다** (= "본문 끝"만 표시. 개정 지침 위반 소지).
4. 각 제휴 링크 자체에 `rel="sponsored nofollow"` 부여 (검색엔진 정책. 공정위 요건과는 별개).

HTML/CSS 예 (이 프로젝트의 규칙 — 외부 라이브러리·웹폰트 0개 — 을 지킴):

```html
<section id="gear" aria-labelledby="gear-h">
  <h2 id="gear-h">세벌식 각인 키보드 고르기</h2>

  <p class="ad-disclosure" role="note">
    광고 · 이 섹션은 쿠팡 파트너스 활동의 일환으로,
    이에 따른 일정액의 수수료를 제공받습니다.
  </p>

  <ul class="gear-list">
    <li><a href="…" rel="sponsored nofollow" target="_blank">…</a></li>
  </ul>
</section>
```

```css
/* 대가성 고지: 본문보다 크고, 본문과 다른 색, 본문과 시각적으로 분리 */
.ad-disclosure {
  font-size: 1.08em;          /* 본문보다 크게 */
  font-weight: 600;
  color: var(--accent);        /* 본문과 다른 색 */
  background: var(--paper-2);
  border: 1px solid var(--accent);
  border-radius: 8px;
  padding: 10px 12px;
  margin: 0 0 14px;
}
```

**체크리스트 (하나라도 아니오면 고쳐라)**

- [ ] 문구가 제휴 링크보다 **위**에 있고, 링크와 **같은 화면**에 보인다
- [ ] 글자 크기가 본문보다 **크다** (또는 색이 본문과 확실히 다르다) — 둘 다면 더 좋다
- [ ] 배경/테두리로 본문과 **구분**된다
- [ ] "일정액의 수수료를 제공받습니다"처럼 **대가의 내용이 명시**돼 있다
- [ ] "협찬받았을 수도 있습니다", "일부 링크는" 같은 **조건부·모호 표현이 없다**
- [ ] 접기(`<details>`), 툴팁, 이미지 안 텍스트, `aria-hidden` 뒤에 숨기지 **않았다**
- [ ] 다크모드에서도 대비가 충분하다 (색으로만 구분한 경우 특히)
- [ ] 푸터에만 있지 **않다**

## 2. Google AdSense

> **중대 제약**: `support.google.com`이 이그레스 차단되어 **애드센스 공식 문서 원문을 한 줄도 직접 읽지 못했다.**
> 이 장은 전부 검색 결과 요약과 커뮤니티 스레드 기반이다. 실제 신청 전 아래 URL을 **직접 열어 확인할 것.**

### 2.1 `*.github.io` 서브도메인으로 신청 가능한가

**결론: 신규 애드센스 계정을 `username.github.io`로 신청하는 것은 사실상 막혀 있다고 보고 계획을 세워라.** **[부분확인]**

근거 3가지:

1. **애드센스는 서브도메인을 개별 승인하지 않고 "부모 도메인의 상태"를 따른다.**
   서브도메인은 부모 도메인이 승인돼 있으면 자동으로 그 상태를 물려받는 구조다. **[부분확인]**
2. **계정은 서브도메인이 아니라 primary domain으로만 개설된다.**
   "AdSense accounts can only be set up on primary domains (e.g. website.com) and not subdomains" —
   서브도메인은 **계정 개설 이후 Sites 목록에 추가**만 가능. **[부분확인]**
3. **부모 도메인 `github.io`의 소유권을 당신이 증명할 수 없다.**
   Google Site Kit 이슈 트래커에 `mysite.wordpress.com`, `mysite.instawp.com` 등
   "부모 도메인을 절대 승인받을 수 없는 서브도메인" 문제가 명시적으로 제기돼 있고,
   `username.github.io`는 정확히 같은 부류다. **[부분확인]**

**미확인으로 남은 것**:
- 애드센스가 Public Suffix List(=`github.io`가 등재돼 있음)를 존중해
  `username.github.io`를 **독립 사이트로 취급**하는지. **[미확인]** — 이게 되면 승인이 가능해진다.
- 커뮤니티에는 `github.io`로 승인받았다는 주장과 거부당했다는 주장이 **둘 다** 있다. **[미확인]**
- 이미 승인된 계정을 가진 사람이 `github.io` 사이트를 Sites에 추가하는 경우의 성공률. **[미확인]**

### 2.2 `ads.txt` — github.io에서는 **원리상 불가능**

규칙: **ads.txt는 도메인 루트에 있어야 한다** (`example.com/ads.txt`).
서브도메인에 둘 수는 있지만, 그 경우 **루트 도메인의 ads.txt에서 참조(위임)되어 있어야** 크롤·집행된다. **[부분확인]**

→ `username.github.io`의 루트 도메인은 **`github.io`**이고 그 `ads.txt`는 GitHub만 통제한다.
→ **`username.github.io/ads.txt`를 올려도 위임 참조가 없으므로 유효하지 않다.** **[추론]**
→ 게다가 **프로젝트 페이지**(`username.github.io/repo/`)라면 파일이 `/repo/ads.txt`에 놓여
   경로 자체가 루트도 아니다. (유저/오거니제이션 사이트 = `username.github.io` 레포여야 `/ads.txt`로 서빙됨) **[추론]**

**즉 애드센스를 제대로 하려면 커스텀 도메인이 실질적 전제조건이다.**

### 2.3 커스텀 도메인 붙이기 + ads.txt 배치

> `docs.github.com` 접속 차단으로 **DNS 레코드 값을 원문 확인하지 못했다.**
> 아래 절차의 뼈대는 맞지만 **IP 주소·CNAME 대상 값은 반드시 GitHub 공식 문서에서 직접 복사할 것.** **[미확인]**

공식 문서 (직접 열어볼 것):
- https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site
- https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/verifying-your-custom-domain-for-github-pages

절차 (뼈대):

1. 도메인 구매 (`.com` / `.kr` / `.dev` 등. 가비아·후이즈·Cloudflare Registrar 등)
2. GitHub 계정 설정 → Pages → **도메인 verification** (DNS TXT 레코드 추가).
   → 이걸 해야 다른 사람이 같은 도메인을 자기 Pages에 붙이는 걸 막는다(도메인 탈취 방지)
3. DNS 설정
   - **apex** (`keymiles.kr`) → GitHub Pages 전용 **A 레코드 4개** (+ AAAA 4개)
     *(실제 IP 값은 GitHub 문서에서 복사 — 여기 적으면 오래된 값을 쓰게 될 위험)*
   - **www** (`www.keymiles.kr`) → **CNAME → `<username>.github.io.`**
   - 가장 단순한 안전 경로: **www를 정본으로 쓰고 apex는 리다이렉트**
4. 레포 Settings → Pages → Custom domain 입력 → 저장
   → 레포 루트에 `CNAME` 파일이 자동 생성됨 (내용: 도메인 한 줄). **이 파일을 지우지 말 것**
5. DNS 전파 후 **Enforce HTTPS** 체크 (Let's Encrypt 인증서 자동 발급)
6. **`ads.txt`를 레포 루트에 추가** → `https://keymiles.kr/ads.txt`로 서빙됨

   ```
   google.com, pub-0000000000000000, DIRECT, f08c47fec0942fa0
   ```
   (`pub-…`는 본인 게시자 ID. 마지막 값 `f08c47fec0942fa0`은 Google의 고정 인증기관 ID — **[미확인]**, 애드센스 화면에 나오는 줄을 그대로 복사할 것)

7. 애드센스에서 사이트를 **`keymiles.kr`(apex)**로 등록.
   www와 apex 중 **ads.txt가 실제로 서빙되는 쪽**과 등록 도메인이 일치해야 함 **[추론]**

**빌드 스텝 없는 정적 사이트라 `ads.txt`는 그냥 레포 루트 텍스트 파일 하나면 끝난다.** 이 프로젝트에 잘 맞는다.

### 2.4 승인에 필요한 페이지 · 콘텐츠 요건

**[부분확인]** — 아래는 Google이 명문화한 "체크리스트"가 아니라 **널리 통용되는 실무 기준**이다.
Google 공식 문구는 "고유하고 가치 있는 콘텐츠" 정도로만 추상적이다.

필수 고정 페이지:

| 페이지 | 필요성 | 비고 |
|---|---|---|
| **개인정보처리방침** | 사실상 필수 | 3장 초안 사용. **모든 페이지에서 링크**돼야 함 |
| **소개(About)** | 사실상 필수 | 누가 왜 만들었는지. 700~1,000자 이상 권장 |
| **문의(Contact)** | 사실상 필수 | 정적 사이트라 폼 불가 → **이메일 주소 텍스트**면 충분 |
| **이용약관 / 면책 고지** | 권장 | "계산 결과는 참고용" 류 |

콘텐츠 요건 (통용 기준):
- 오리지널 글 20~30편, 편당 800자+ **[미확인]** (수치는 블로그 기준. 도구 사이트에는 그대로 적용되지 않을 수 있음)
- 도메인 3~6개월 이상 운영 **[미확인]**
- HTTPS, 모바일 대응, 제한 콘텐츠 없음
- 고정페이지에 **광고 클릭 유도 문구 없을 것**, 외부 콘텐츠 무단 인용 없을 것 **[부분확인]**

> **손가락 마일리지의 진짜 리스크**: 이 사이트는 "도구 1개 + 짧은 설명"이라
> **"가치가 별로 없는 콘텐츠(low value content)"** 사유로 반려될 확률이 실제로 높다. **[추론]**
> 대응: `index.html`의 `#learn` 섹션을 **독립 문서 여러 편**으로 키워라 —
> 두벌식 표준 제정사, 세벌식 390 vs 최종 차이, SFB가 왜 문제인지, 측정 방법론(GEOM 근거),
> 다른 계산기와 결과가 다른 이유 등. 이건 어차피 사이트의 신뢰도 자산이다.

### 2.5 광고 배치 정책상 금지 사항

**[부분확인]** — 공식: https://support.google.com/adsense/answer/1346295?hl=ko (게재위치 정책),
https://support.google.com/adsense/answer/2660562?hl=ko (계정 해지로 이어지는 위반)

금지:

1. **클릭 유도** — 어떤 방식으로든 의도적으로 클릭을 유도하는 행위
2. **기만적 배치** — 광고를 **메뉴 / 내비게이션 / 다운로드 링크처럼 보이게** 하는 구현
3. **콘텐츠 없는 화면에 게재** — 게시자 콘텐츠가 없는 페이지, **광고 목적으로만 만든 페이지**
4. **보상 제공** — 클릭에 대한 대가/인센티브 제공
5. **Google 사칭** — 로고·상표를 부적절히 써서 Google 관련 콘텐츠/URL인 것처럼 오인시키는 배치

> **손가락 마일리지에서 특히 위험한 지점** **[추론]**:
> - 결과 카드(`results`) 사이에 광고를 끼우면 **"결과의 일부처럼 보이는"** 기만적 배치가 된다.
>   → 광고 위에 `광고` 라벨을 명시하고, 카드와 다른 배경/여백으로 확실히 분리할 것.
> - 「분석하기」 버튼 근처에 광고를 두면 **오클릭 유도**로 읽힌다. 버튼 주변 최소 여백 확보.
> - **분석 결과가 나오기 전 빈 상태 화면**은 "콘텐츠 없는 화면"에 해당할 수 있다.
>   → 자동 광고(Auto ads)를 켜지 말고 **수동 배치**로, 결과가 렌더된 뒤에만 노출되는 슬롯을 쓸 것.
> - 이 사이트는 사용자가 **자기 카톡 로그를 붙여넣는** 도구다.
>   광고 스크립트가 붙는 순간 "브라우저 밖으로 안 나간다"는 약속의 **설명 책임**이 커진다(3장 참조).

### 4.2 CORS — 직접 검증하지 못했다 (중요)

프록시가 외부 HTTP 요청을 403으로 차단해 **실제로 호출해보지 못했다.** 문헌 기준만 정리한다.

**Lemon Squeezy License API** **[부분확인]**
- 엔드포인트 3개: `POST /v1/licenses/activate`, `/validate`, `/deactivate` (base: `https://api.lemonsqueezy.com`)
- **이 3개는 API 키가 필요 없다** (라이선스 키 자체가 자격증명). → 정적 사이트에서 부를 수 있는 유일한 후보.
- 헤더: `Accept: application/json`, `Content-Type: application/x-www-form-urlencoded`
- **CORS**: 공식 문서에 `Origin`이 `null`인 환경(샌드박스 iframe 등)을 위한
  **`https://api-cors-anywhere.lemonsqueezy.com` 프록시**가 안내돼 있다.
  → 프록시를 별도로 안내한다는 것은 **일반 브라우저 Origin에서는 CORS가 열려 있을 가능성이 높다**는 뜻이다. **[추론, 미검증]**
- 공식 경고: **"클라이언트 사이드 JS나 데스크톱 바이너리에서 LemonSqueezy API를 직접 호출하지 말라"** —
  단 이 경고의 주된 이유는 **API 키 노출**이므로, 키가 불필요한 License API 3종에는 논리가 그대로 적용되지 않는다. **[추론]**

**Gumroad License Verify** **[미확인]**
- `POST https://api.gumroad.com/v2/licenses/verify`, 파라미터 `product_id`, `license_key`, `increment_uses_count`
- 2023-01-09 이후 생성된 상품은 `product_permalink`가 아니라 **`product_id`** 필수
- **API 키 불필요**
- CORS 여부: **자료에서 확인 불가.** 발견된 예제는 전부 Node.js 서버 사이드.

**직접 확인 방법** — 네트워크가 열린 환경에서 이걸 그대로 실행하면 5초 안에 답이 나온다:

```bash
# 프리플라이트 응답에 Access-Control-Allow-Origin 헤더가 있는지 본다
curl -s -D - -o /dev/null -X OPTIONS \
  "https://api.gumroad.com/v2/licenses/verify" \
  -H "Origin: https://keymiles.kr" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type"

curl -s -D - -o /dev/null -X OPTIONS \
  "https://api.lemonsqueezy.com/v1/licenses/validate" \
  -H "Origin: https://keymiles.kr" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type,accept"
```

또는 브라우저 콘솔에서 (가장 확실):
```js
fetch('https://api.lemonsqueezy.com/v1/licenses/validate', {
  method: 'POST',
  headers: { 'Accept': 'application/json',
             'Content-Type': 'application/x-www-form-urlencoded' },
  body: 'license_key=00000000-0000-0000-0000-000000000000'
}).then(r => r.json()).then(console.log).catch(console.error);
```
→ JSON이 돌아오면 CORS 열림. `TypeError: Failed to fetch` + 콘솔에 CORS 에러면 막힘.

### 4.3 서버 없는 라이선스 검증의 한계 — 정직하게

**결론: 서버 없이 "진짜" 라이선스 검증은 불가능하다.** 다음 세 가지가 전부 뚫린다.

1. **검증 코드가 클라이언트에 있다.**
   `if (licenseValid) unlock()` 한 줄을 DevTools에서 `licenseValid = true`로 바꾸면 끝난다.
   난독화는 시간을 몇 분 늘릴 뿐이다.
2. **소스가 공개돼 있다.**
   GitHub Pages 정적 사이트는 `view-source:`로 전체 로직이 보인다.
   레포가 public이면 아예 파일째로 읽힌다.
3. **검증 결과를 캐시해야 한다.**
   매번 API를 부를 수 없으므로 `localStorage`에 "인증됨"을 남긴다 →
   그 키를 직접 써넣으면 결제 없이 통과한다.

부분적으로 유효한 완화책 (**완전하지 않음, 시간벌기용**): **[추론]**

- **워터마킹**: 무료판 내보내기 PNG/SVG에 워터마크 → 워터마크 제거 로직도 클라이언트에 있으므로 우회 가능하나, "결제 안 한 티가 남는" 사회적 억지력은 실재
- **HMAC 서명 키**: `사용자이메일|만료일|서명` 형태의 키를 발급하고 사이트에는 **검증용 공개키만** 둔다(예: Ed25519 서명 검증).
  → 키를 **위조**하는 건 어려워지지만, **검증을 건너뛰는** 건 여전히 쉽다. 즉 "키 생성기(keygen)"는 막고 "패치"는 못 막는다.
- **오프라인 검증 우선**: 어차피 뚫리니 네트워크 호출 자체를 없애고 서명 검증만 하면 CORS 문제도 사라지고 개인정보 이슈도 사라진다. **이 사이트에는 이 조합이 가장 잘 맞는다.**
